shinygen

Generate, evaluate, and refine Shiny apps using LLM agents in Docker sandboxes

shinygen turns a text prompt into a production-quality Shiny dashboard — generated, screenshot-tested, and quality-scored — all inside an isolated Docker sandbox.

Core Capabilities

Multiple LLM Agents

Leverages Claude Code (via Anthropic), Codex CLI (via OpenAI), Gemini CLI (via Google), and OpenCode (via OpenCode Go) to autonomously write clean and professional app layouts.

Docker Isolation

Generations run in isolated containers using Inspect AI, protecting your host system from side-effects.

Visual Self-Correction

The sandbox agent takes local Playwright screenshots, reviews layout rendering, and dynamically corrects visual styling before submission.

Multi-Judge Evaluation

An external, host-side LLM panel scores code quality, visual design, functionality, and UX, feeding back critiques for refinement.

Iterative Refinement

Runs automated generate-judge-refine cycles until code meets the quality threshold, up to --max-iterations.

Custom Skills Injection

Pass custom guidelines and component directories to enforce branding rules, library preferences, and modern coding standards.

A/B Benchmark Arms

Compare treatment (--skills) vs control (--no-skills) to measure exactly how much your skill rules improve generation scores.

Web Search Fetching

Allows agents to fetch up-to-date documentation and examples from the live web. Can be disabled with --no-web-fetch.

Installation & Requirements

Quick Install

Install shinygen via pip in editable mode:

git clone https://github.com/karangathe/shinygen.git
cd shinygen
pip install -e .

If you plan to use screenshot-based visual evaluation and host-side verification, install the playwright extras:

pip install -e ".[screenshot]"
playwright install chromium
Tip

Docker sandbox images containing R, Python, Playwright, and headless Chromium are pulled and built automatically on your first generation run.

Quick Start Guide

You can run shinygen either through the CLI command shinygen generate or via the programmatic Python API.

  • Python Dashboard (CLI)
  • R Dashboard (CLI)
  • Programmatic API
  • Batch Generation
# Generate a Python-based Shiny app with Claude Sonnet
shinygen generate \
    --prompt "Create a sales dashboard with filters by region and product category" \
    --model claude-sonnet \
    --output ./my-dashboard
# Generate an R-based Shiny app (shiny-r)
shinygen generate \
    --prompt "Create an interactive mtcars data explorer with ggplot2 charts" \
    --model claude-sonnet \
    --framework shiny-r \
    --output ./my-r-dashboard
import shinygen

result = shinygen.generate(
    prompt="Create a clinical trials dashboard with enrollment trends",
    model="claude-sonnet",
    output_dir="./trials-app",
    framework="shiny-python",
    data_csv="./trials_data.csv",
    screenshot=True,
    judge_model="openai/gpt-5.6-luna",
    max_iterations=3,
)

print(f"Generated app path: {result.app_dir}")
print(f"Score: {result.score:.2f} (Passed: {result.passed})")

Evaluate multiple models or prompts sequentially. Create a JSON config file mapping jobs:

batch.json
[
  {
    "prompt": "Create a clinical trials dashboard with enrollment trends",
    "model": "claude-sonnet",
    "output_dir": "./batch/sonnet",
    "csv_file": "./trials_data.csv",
    "screenshot": true,
    "judge_model": "openai/gpt-5.6-luna"
  },
  {
    "prompt": "Create a clinical trials dashboard with enrollment trends",
    "model": "gpt-5.6-luna",
    "output_dir": "./batch/gpt56",
    "csv_file": "./trials_data.csv",
    "screenshot": true,
    "judge_model": "openai/gpt-5.6-luna"
  }
]

Then run the batch config:

shinygen batch --config batch.json

Architecture & Sandbox Deep Dive

The Execution Loop

shinygen orchestrates a closed feedback loop: it runs the coding agent, spins up the application, takes screenshots, rates the visual output via an external LLM, and refines the code iteratively.

Docker Sandboxing Mechanics

Every generation job occurs inside an isolated Docker sandbox managed via Inspect AI. - Images Used: - Python: ghcr.io/karangattu/shinygen-sandbox-python:latest - R: ghcr.io/karangattu/shinygen-sandbox-r:latest - Isolation Boundaries: The agent cannot see or modify files on your host machine. It can only read and write inside /home/user/project inside the container. - Auto-dependency Installation: On startup, shinygen executes the framework’s install command (pip install ... or install.packages(...)) to ensure all necessary rendering and plotting libraries (like plotly, bslib, faicons, ggplot2) are hot-loaded in the sandbox. - Web Search: The agent has internet access to look up API docs and download styling examples. Disable this by passing --no-web-fetch (which blocks the web search tool).

Visual QA & Validation

Hands-on Agent Self-Evaluation

When --screenshot is enabled, the sandbox agent leverages the visual-qa skill: 1. The agent starts the Shiny app inside the container as a background daemon (using nohup ... &). 2. It runs screenshot_helper.py to capture a Playwright screenshot on http://localhost:8000. By default, it pauses for 7 seconds (configurable) to allow JavaScript/charts to load completely. 3. The agent reviews the screenshot, identifies design flaws (e.g., overlapping text, unstyled charts, missing headers), modifies the code, and takes another screenshot until it is satisfied. 4. It terminates the background daemon before submitting the final draft.

Host-Side Verification & Logging

Once the agent completes its run, shinygen performs a host-side runtime check: - It launches the app on the host machine using a dynamically allocated free port (validated range 1-65535). - It captures startup logs. If the app crashes on launch, shinygen catches the traceback and feeds it directly into the next iteration’s refinement prompt. - It takes host-side Playwright screenshots to pass to the external LLM judge.

Quality Evaluation & Value-Based Scoring

Multi-Judge Panel

If --judge-model is specified, shinygen routes code and host-side screenshots to an external LLM judge (or a panel of judges, if the flag is repeated).

NoteJudge Validation & Retries

The judge model must be fully qualified starting with anthropic/, openai/, or google/ (e.g., openai/gpt-5.6-luna). Unknown model providers will raise validation errors. Judge calls use automatic retry with exponential backoff (up to 3 attempts) for robustness against rate limits.

The judges evaluate the dashboard across four strict criteria:

  1. Requirement Fidelity: Does the app implement all requested tabs, charts, filters, and datasets?
  2. Code Maintainability: Is the code modular, DRY (Don’t Repeat Yourself), cleanly formatted, and easy to modify?
  3. Visual & UX Quality: Evaluates human-perceived visual quality from rendered screenshots — whether the dashboard looks clear, useful, cohesive, trustworthy, and complete at first glance. Key standards include:
    • One-Screen Usefulness (5-Second Rule): The landing view must immediately communicate the subject, 3–4 concise KPIs, a prominent primary visualization, and an actionable analytical story. Extra tabs add depth but cannot repair a weak first impression.
    • Render-State Gate: Visible screenshot evidence overrides code intent. Repeated empty cards, stuck spinners, tiny placeholder marks, or unresolved outputs cap visual_ux_quality at 3 even when surrounding chrome is polished.
    • Layout & Structure: Consistent grid alignment, comfortable spacing, and clear visual hierarchy (primary KPIs prominent, secondary views subordinated) without wasted whitespace or cramped tiles.
    • Typography & Color: Refined type scales (distinct header, section, body, caption weights), readable line-height, restrained color palettes (2–4 semantic accents), and high-contrast elements (WCAG AA).
    • Component & Chart Legibility: Grouped controls with clear labels, value boxes with meaningful icons/units/deltas, zebra-striped tables with aligned numerics, and charts with explicit titles, labeled axes, units, and restrained palettes (no default plotly rainbow or raw unstyled axes).
    • State Polish & Graceful Errors: Handled empty and loading states without raw tracebacks or broken layouts across viewports.
  4. Code Robustness: Graceful error handling (no raw tracebacks visible to users), empty states handled cleanly, and stable reactive bindings.

Visual & UX Quality Calibration Scale

Visual & UX Quality Judge Rubric
Score Assessment
1–3 Broken, loading, or repeatedly empty visible outputs.
4 Confusing, cramped, patchwork, or substantially incomplete dashboard.
5 Mixed visual hierarchy, awkward density, weak chart choice, or poor coherence.
6 Tidy but basic, sparse, weakly prioritized, or visually generic (typical default layout).
7 Clear, trustworthy dashboard with strong information density and legible charts.
8 Strong professional composition, coherent palette, polished components, and immediately useful landing view.
9 Exceptional human favorite: cohesive, information-rich, beautifully styled, and complete.
10 Essentially unreachable (flawless in every dimension with zero possible improvement).

Value-Based Scoring Formula

Instead of raw quality alone, shinygen optimizes for value-adjusted scores to penalize wasteful API calls:

\[\text{value\_score} = \text{quality\_score} - \text{iteration\_penalty} - \text{cost\_penalty}\]

Where: - Iteration Penalty: Deducts \(0.35\) for each extra generation iteration. - Cost Penalty: Deducts \(1.00\) per \(\$1.00\) of API generation cost (capped at a maximum deduction of \(2.50\)).

This formula ensures models that get the dashboard right in the first iteration at lower costs score higher than models that take many expensive correction steps.

Custom Skills Injection & A/B Benchmarks

Injecting Custom Skills

“Skills” represent styling guides, code templates, and coding standards injected into the agent’s workspace. - Standard Skills: shinygen dynamically fetches the official app-authoring skills at runtime and caches the latest successful download: shiny-for-python from posit-dev/py-shiny and shiny-for-r from rstudio/shiny. Set SHINYGEN_PY_SHINY_SKILL_REF or SHINYGEN_R_SHINY_SKILL_REF to use specific tags or commits instead of main. - Custom Skills: You can inject your own guidelines (e.g. company styling themes, database query layers) using --skills-dir <path>.

Creating a Custom Skill Directory

To write your own skill, create a folder with the following structure:

my-custom-skills/
├── SKILL.md                 # REQUIRED: Contains skill description and YAML frontmatter
└── references/              # OPTIONAL: Supporting markdown guides
    ├── cards.md
    └── theming.md

Your SKILL.md must start with a YAML frontmatter block:

---
name: corporate-theme-skill
description: Guidelines for styling dashboards using the corporate HSL color palette.
metadata:
  version: "1.0"
---

# Corporate Styling Guidelines
- Use CSS variables for color branding.
- Avoid absolute positioning.

Inject your custom skill using:

shinygen generate --prompt "Sales App" --skills-dir ./my-custom-skills/

Control vs Treatment Arms (A/B Testing)

You can benchmark skill effectiveness using the control/treatment flags: - Treatment Arm (--skills): Injects the framework skill plus any custom skills. - Control Arm (--no-skills): Bypasses skill loading entirely. The agent receives only the raw prompt.

shinygen tracks the arm used (skills or vanilla) inside the resulting run_summary.json to calculate the lift in quality score.

Model Ecosystem

Model Types

shinygen routes across three distinct tiers of LLMs:

  1. Frontier Models: Run in Docker containers (Claude Code, Codex CLI, Gemini CLI).
  2. OpenCode Go Models: Routed via the OpenCode agent in Docker containers. API calls are authenticated using OPENCODE_GO_API_KEY and target https://opencode.ai/zen/go/v1.
  3. Local Models via LM Studio: Run unmetered local evaluations (e.g., gemma-4-26b-a4b or qwen3.6-27b):
    • Runs entirely on the host (Docker check is bypassed).
    • Bypasses API key verification.
    • Sets pricing to $0.00 so value-based scores are not penalized by token usage.
    • Targets the local server on http://localhost:1234/v1 (configurable via LMSTUDIO_BASE_URL).

DashSwipe: Interactive Dashboard User Testing

To help align dashboard styles, this repository includes DashSwipe, an interactive user-testing survey application located in the user_testing_app/ directory.

  • Purpose: Collects human feedback on LLM-generated layouts. It serves screenshots anonymously, lets users tier-rank layouts (S/A/B/C/D/F), prompts for 2-word critiques, and writes evaluation statistics directly to a Supabase database.

  • Run Locally:

    python3 -m http.server 8080 --directory user_testing_app

    Open http://localhost:8080/ in your browser.

  • Database Schema: Refer to user_testing_app/README.md to set up the Postgres schema.
